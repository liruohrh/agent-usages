# 输出与格式

## 各表的列

每一张表都带同一组 token 列，否则表与表之间无法对照（`总量` 有七个口径，而 `按项目` 只有三个时，就没法核对）。列名是缩写，七个全名会把表撑出终端宽度：

| 列名 | 含义 |
| --- | --- |
| `I` | 未命中缓存的输入 |
| `I/C` | 缓存命中输入（cache read） |
| `I/W` | 缓存写入输入；该来源不写入时不出现 |
| `I/T` | 输入合计 |
| `O` | 输出（非思考） |
| `O/R` | 输出（思考，reasoning） |
| `O/T` | 输出合计，即供应商报告的 completion 数 |
| `T` | Token 总计 |

| 表 | 列 |
| --- | --- |
| 总量 | 七项 token 逐行（标签同左表） |
| 按范围 | 会话 / 请求 / 七项 token / 货币符号 / 占比 |
| 模型明细 | `M`（模型） / 请求 / 七项 token / 货币符号 |
| 按项目 | 会话 / 子代理 / 请求 / 七项 token / 货币符号（**含合计行**） |
| 按会话 | `↳` 标记 / 子代理 / 请求 / 七项 token / 货币符号（**含合计行**） |

金额列的表头直接用计价来源的货币符号（DeepSeek 是 `¥`），模型列的表头是 `M`。

另外两张表各司其职，**不与上面的 token 口径混列**：

- **`费用明细`**：按计费项拆金额（计费项 / 计费 token / 货币符号）。这里的 token 是「按该项单价计费的 token」，有些来源下是某个桶的一部分、有些跨两个桶（`inputAndCacheWrite`），**相加会重复计数**，所以这张表只对金额求合计。计费项仍用它的全名，因为它按**计费口径**而不是 token 桶命名。单价不在这里给——跨峰谷计费的项没有单一单价。
- **`计价区间`**：按（区间 × 峰谷）给请求数、输入 token（`I/T`）、**该区间的单价表**与金额。单价放这里才诚实：同一批缓存命中可能一部分按空闲价、一部分按高峰价，报表级的「单价」是个假概念。

会话表不再显示会话 ID（原本一列 44 字符把表撑到 200 格以上），标题超过 32 格会截断；完整 ID 在 `session list` 与 `--json` 里。`session list` 是清单，不含 token 列。JSON 输出不受缩写影响，字段名始终是全名。

## Token 统计口径

四个桶**互不重叠**，因此合计是相加而不是取其一：

| 列名 | 行 | 含义 |
| --- | --- | --- |
| `I` | 输入(缓存未命中) | 未命中缓存的 prompt token |
| `I/C` | 输入(缓存命中) | 命中缓存的 prompt token |
| `I/W` | 输入(缓存写入) | 缓存写入 token；该来源不写入时整行隐藏 |
| `I/T` | **输入合计** | 上述三项之和 —— 一次请求的完整 prompt |
| `O` | 输出(非思考) | `输出 − 思考` |
| `O/R` | 输出(思考) | 推理 token |
| `O/T` | **输出合计** | `非思考 + 思考`，即供应商报告的 completion 数 |
| `T` | Token 总计 | 输入合计 + 输出合计 |

**思考 token 是输出的一部分，不是额外部分**：供应商把它报在 completion 计数里面，所以「输出合计」等于供应商自己的 completion 数，思考在其中只计一次。把它单独列出是为了看清推理占比，而不是为了再加一遍。`usage --json` 的 `totals.tokenBreakdown` 给出同一组数字。

**`O/R` 可能是 0**：推理 token 由 provider 上报，新版 DSH 默认的 `messages` 协议不带这个字段（见 [DSH 适配器](agents/dsh.md)），此时思考计 0，但 `O` 与 `O/T` 仍是真实的 completion 数。工具不会去估算。

各桶如何换算成钱，见 [DeepSeek 价格表](pricing/deepseek.md)。

## 对齐规则

所有 `标签  数值` 区块共用同一个标签列宽，表格单元格逐列补齐，宽度一律按**终端显示格数**计算而不是字符个数。

宽度测量用 [`string-width`](https://www.npmjs.com/package/string-width)。这里的坑比看上去深：自写的 `codePoint > 0x2e80` 判断对 CJK 和全角标点是对的，但对下面这些都会算错一格以上，进而让整列错位——

| 输入 | 真实格数 | 朴素判断 |
| --- | --- | --- |
| `ｱｲｳｴｵ` 半角片假名 | 5 | 10 |
| `👨‍👩‍👧` ZWJ 序列 | 2 | 8 |
| `🇨🇳` 区域指示符国旗 | 2 | 4 |
| `❤️` 带变体选择符 | 2 | 3 |
| `é`（e + 组合符） | 1 | 2 |

这些情况都有回归测试（`test/unit/format.test.ts` 的 `terminal width, beyond CJK` 一节）。截断同理：按 **grapheme 簇**切（`Intl.Segmenter`），不会把 emoji 或组合字符切成半个。表格每行（含表头与合计行）宽度完全一致，右侧不会参差。

表格是自己渲染的，没有采用 `cli-table3` / `console-table-printer` / `table`：它们确实也正确处理 CJK（内部同样依赖 `string-width`），但都会引入边框与默认 ANSI 着色，而本工具需要的是无边框、`合计` 行、以及行宽严格一致这些细节；自己渲染约 20 行，也不额外引入依赖树。

## 表格合计行

文本模式的三张表（按项目、按会话、会话列表）在**行数多于一行**时，末尾会补一条 `合计` 行，方便直接核对；只有一行时省略——那时合计与该行完全重复，没有信息量。

合计行取自报表本身的总量，而不是把上面各行相加：行是取整后的显示值，且合并口径下父会话行已经含了子代理，直接相加会得到错的数。

```
按项目:
项目       路径                     会话  子代理   请求  未命中输入  缓存命中   输出      费用
─────────  ───────────────────────  ────  ──────  ─────  ──────────  ────────  ─────  ────────
example-a  /home/user/ws/example-a     1       2    530        439K    123.6M   397K   ¥7.3491
example-b  /home/user/ws/example-b     2       —    184        131K     25.6M   199K   ¥2.4305
example-c  /home/user/ws/example-c     2      42  1,447       1.83M    109.3M  1.66M  ¥14.8963
─────────  ───────────────────────  ────  ──────  ─────  ──────────  ────────  ─────  ────────
合计                                   6      44  2,161       2.39M    258.5M  2.26M  ¥24.6759
```
